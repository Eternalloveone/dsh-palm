# ChatView 重写方案（评估 + 设计）

> 结论先行：**「把 ChatView 重构干净」做不到；「重写一遍」做得到，但有明确前提。**
> 本文给出：能到哪、代价多少、怎么做、怎么验收。
>
> 基线：分支 `refactor/v2`，ChatView **4,138 行**，`useState` 0、`useEffect` 20、
> `useCallback` 32、`useRef` 35、`useMemo` 4；`views/chat/` 已分 4 个子目录（62 模块）。

---

## 一、评估：能不能「重构干净」

分三层回答，因为三层的答案不一样。

| 层 | 能否重构干净 | 依据 |
|---|---|---|
| **组件与目录分层** | ✅ **已经做到了** | 62 个模块分进 `components/hooks/state/lib`，有架构断言守着（14 条） |
| **状态管理** | ✅ **已经做到了** | `useState` 30 → 0，4 个切片 + 纯 reducer，函数式 setter 语义不变 |
| **ChatView 本体的瘦身** | ❌ **重构做不到，只能重写** | 见下面的算术 |

### 为什么本体只能重写

| 事实 | 数字 |
|---|---|
| 剩余 20 个 effect 里**不能搬的派生同步** | 11 个 |
| 剩下 9 个深度耦合（每个搬运要读 100+ 行、牵动 10+ 依赖） | 9 个 |
| 全部搬完后的理论下限 | **≈3,940 行** |
| 距 800 行仍差 | **3,140 行** |

这 3,140 行不是"还没搬的东西"，是**逻辑密度**：45 个钩子调用之间靠 35 个 `useRef`
互相咬合，把任何一个搬到外面都要同时改它的读写方。逐块搬运的边际收益已降到 10~15 行/轮，
**减到 800 需要约 200 轮**。

所以：**"重构"这条路已经被走到尽头了，不是走错，是走到了边界。**

## 二、重写方案设计

### 2.1 目标结构

```
views/chat/
├── ChatView.tsx              ≤250 行   只做装配：读路由参数、拼三块、挂错误边界
├── controller/
│   ├── use-chat-controller.ts ≤400 行  唯一的状态编排层（见 2.2）
│   ├── session.ts             ≤200     会话切换：reset / 快照回填 / 页加载
│   ├── fold.ts                ≤250     折叠与流式合并（EventFolder 的外壳）
│   └── timeline.ts            ≤300     回合/卡片/未读/定位
├── views/
│   ├── ChatHeaderView.tsx     ≤200     顶条 + 搜索条 + 离线横幅
│   ├── MessageListView.tsx    ≤350     .chat-scroll + 行 + 滚动控件 + 注意力面板
│   └── ComposerDock.tsx       ≤300     输入区 + 四个 sheet + 菜单
└── （现有 components/hooks/state/lib 原样保留，作为被调用方）
```

**关键约束**：三块视图**只接收 props，不读全局、不发请求**。所有副作用收敛在 `controller/`。

### 2.2 controller 的接口（唯一契约）

```ts
interface ChatController {
  // 数据
  rows: readonly RenderRow[]
  header: HeaderModel      // 标题、模型、权限、连接状态
  composer: ComposerModel  // 草稿、附件、排队、目标条
  // 动作（全部是命令，不是 setter）
  actions: {
    send(text: string): Promise<void>
    stop(): void
    loadOlder(): Promise<void>
    jumpTo(turn: number, seq?: number): void
    setDraft(text: string): void
    retryCard(turn: number): void
  }
  // 状态机现状（用于断言与调试，不用于渲染分支）
  phase: 'loading' | 'ready' | 'offline' | 'error'
}
```

**为什么是命令而不是 setter**：现在 45 个钩子互相能写状态，重写后只有 controller 能写。
视图想改什么必须走 `actions`，这一步把"谁能改什么"从注释变成类型。

### 2.3 迁移步骤（每步独立可验证）

| 步 | 做什么 | 完成标志 | 估时 |
|---|---|---|---|
| R0 | 打基线：把现有 244 条 ChatView 用例 + S0 指纹固化为**重写验收套件** | 套件在旧实现上全绿 | 0.5 天 |
| R1 | 抽出 `controller/session.ts`（会话切换那 60 行），旧实现改为调用它 | 全绿 | 0.5 天 |
| R2 | 抽 `controller/fold.ts` + `timeline.ts` | 全绿 | 1 天 |
| R3 | 写 `use-chat-controller.ts`，把现有 45 个钩子按域**收编**进去（不是重写逻辑，是换装配） | 新旧输出一致 | 1 天 |
| R4 | 拆三块视图，`ChatView.tsx` 变装配层 | 行数 ≤250，全绿 | 1 天 |
| R5 | 删旧路径 + 加断言（视图不许直接 import `api.ts` / 不许 `useEffect`） | 断言全绿 | 0.5 天 |

合计 **4.5 天**（不含真机验证）。

### 2.4 风险与对策

| 风险 | 概率 | 对策 |
|---|---|---|
| 折叠/流式合并行为漂移（最隐蔽） | 中高 | R2 前先把 `EventFolder` 的输入输出做 200 组快照对比 |
| 滚动与定位在真机上错位 | 中 | 每步都跑 S0 指纹 + 真机三点位（顶部/中部/底部）手测 |
| 视图拿不到需要的字段，被迫回读 context | 中 | 允许 controller 暴露只读选择器，**不允许**视图持有写入口 |
| 4.5 天估时偏乐观 | 高 | R1 是试金石：若 R1 超出 1 天，说明耦合比估计更深，应停下来重估 |

## 三、验收标准（可执行）

重写完成后，必须同时满足：

1. `ChatView.tsx` **≤250 行**（当前 4,138）
2. `controller/` 四个文件合计 **≤1,150 行**
3. 三块视图合计 **≤850 行**，且**零 `useEffect`**
4. 现有 **244 条 ChatView 用例 + S0 指纹**不改一行、全绿
5. 新增 3 条断言：视图不许 import `../api.ts`、视图不许 `useEffect`、controller 不许 import `../views/`
6. 真机手测：进入会话 / 发送 / 停止 / 翻历史 / 搜索定位 / 断网重连 六个动作无回归

---

## 四、不做的代价

| 选择 | 结果 |
|---|---|
| **不做重写**（停在现在） | 4,138 行的文件长期存在；新功能继续往里加，两年后回到 5,000+。分层与断言能防止它**变烂**，但拦不住它**变大** |
| **做重写** | 4.5 天 + 真机验证，换来一个能在 250 行里读完的入口 |

**一句话建议**：如果你未来还要在这个页面上加功能，做重写；如果这个页面已经冻结，停在现在就好——现在的状态是**可维护的**，只是**不可读**。
