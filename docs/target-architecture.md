# dsh-palm 目标架构（我的主张）

> 一句话：**五个环，依赖只向内；屏幕是纯函数；样式零运行时；边界用断言守，不用 ESLint。**
> 不换技术栈、不拆包、不引状态库、不上虚拟列表。

---

## 一、目标形态：五环

```
① 外壳 app/            ≤400 行    唯一入口：路由 + 组装 model + 暴露 actions
       ↓
② 屏幕 features/       9 屏       纯展示：只吃 model 切片，只调 actions，零请求零 useEffect
       ↓
③ 组件 components/     ~15 个     特性无关的组合件（Sheet / 队列坞 / 目标条 / 图标…）
       ↓
④ 内核 ui/             ~9 个      纯原子件（menu / overlay / primitives / sheet / focus-trap）
       ↓
⑤ 样式 styles/ + design/         42 个 CSS 分 @layer + 语义 token（明暗两套）

旁路（同样只向内）：
   platform/   网络·存储·构建·性能·通知·语音·导出      （设备与宿主边界）
   stream/     事件流·会话仓·运行态·滚动状态机
   render/     折叠模型·markdown·代码/diff·行渲染
   session/    缓存·快照·大纲·审批批次
   api/        服务端路由（按域拆，与 host/ 的 10 个域对齐）
```

**依赖方向只有一条**：①→②→③→④→⑤，旁路层只能被 ② 及以上引用，**不许反向**。

---

## 二、六条不可谈判的规则

| # | 规则 | 怎么守 |
|---|---|---|
| 1 | 屏幕层零数据访问（不 import `api` / `data` / `store`） | 架构断言（现状：只对 `views/chat` 断言，要扩到全部 9 屏） |
| 2 | 屏幕层零 `useEffect` | 同上（现状：ChatView 已 0 useState，effect 剩 20 个待迁） |
| 3 | `ui/` 内核不许 import `components/`、屏幕、数据层 | 已有断言，保持 |
| 4 | 特性之间只经 `types` 通信，不许深导入对方内部 | 新增断言（白名单式） |
| 5 | 样式零运行时，只许构建期拼接 | 已有 `mobile-styles.freshness` 断言 |
| 6 | 行数预算只降不升 | 已有预算表，每步同步下调 |

**为什么不用 ESLint**：项目现在没有 ESLint（无依赖、无配置、无 lint 脚本），引入它要配规则 + 修存量 + 接 CI，约 2 天；而 14 条架构断言体系已经在跑，加一条只要 0.5 小时。**同一种能力，用已经有的那个。**

## 三、分期（每步独立可发布、可回滚）

| 期 | 内容 | 工期 | 完成标志 |
|---|---|---|---|
| **P0 护栏** | 3 条新断言（特性间深导入 / ui 不许向上 / 9 屏都守数据访问）+ 2 处时间注入 | 0.5 天 | 故意违规 → 断言红 |
| **P1 设计系统** | 语义 token 补全（别名层）+ 4 个基础组件（Button / Field / Sheet / ListRow）+ CSS 分 `@layer` + 3 条治理断言 | 2 天 | 新页面只用这 4 个组件就能拼出来 |
| **P2 外壳与屏幕** | `App.tsx`（1,259）→ `app/shell.tsx`（≤400）：路由表 + `model` 组装 + `actions`；先迁 Settings（783），再列表两屏，ChatView 最后 | 3 天 | 9 屏合计 10.3k → **≤7k**；每屏零 `useEffect` |
| **P3 平台接口化** | `storage` / `notify` 先抽（小），`mux` 后抽（990 行，含重连/背压） | 3 天 | 核心流程测试改用注入的假实现，不再 mock `fetch` |
| **P4 渲染优化** | 消息行 memo 分层（历史行冻结，仅最后一行订阅流式） | 2 天 | S0 指纹 diff 为零 + 长会话滚动有前后对比数据 |
| **P5 服务端** | `mobile-api.ts`（3,848）按域搬进 `api/{sessions,chat,settings,…}.ts` | 3 天 | 与 `host/` 的 10 域对齐，单文件 ≤800 |

**合计 ≈ 13.5 天**（不含返工）。顺序的关键：**P4 必须最后**——结构一动，memo 就白做。

## 五、我明确不做的事（及其重估条件）

| 不做 | 重估条件 |
|---|---|
| 拆 monorepo | 出现第二个消费方（例如独立 Web 版） |
| 换状态库 | 现有 reducer 无法表达某个真实交互（不是"觉得啰嗦"） |
| 虚拟列表 | 单会话 >800 条 **或** 单条 diff >200 行 |
| SSE Worker | 主线程解析耗时 >16ms/帧（需先测） |
| 原子类 / 换构建链 | 出现现有零运行时方案表达不了的样式需求 |

---

## 六、为什么是这个而不是别的

- **不是**"按 feature 重切目录"：A 步刚做完，目录已经是按域分的，再切是重复劳动。
- **不是**"照搬 Clean Architecture / DDD 四层"：层数比问题多，移动端会变成仪式。
- **不是**"一次大重写"：9 屏 1 万行 + 2,666 条测试，一次性替换的回归面不可控；分屏迁移能把风险切成 9 份。

**核心判断**：这个项目的问题不是"分层不对"，而是 **① 缺少组件层（只有 token 没有组件）、② 外壳和屏幕长在一起、③ 平台层没有接口**。上面五期分别对应这三件事。
