# 重写后的项目架构（分层 / 依赖方向 / 与五原则对照）

> 实测基线：`packages/dsh-palm/src` 共 **88,839 行**（其中 `mobile-styles.ts` 9,378 行是
> `src/mobile/styles/` 的**生成副本**，真实代码约 79,000 行）。
> 本文描述**重写后**（完成 U0–U6）应有的形状，并逐条对照五个原则。

---

## 一、分层图（依赖只能向下，不能反向）

```
┌─ L5 入口层 ────────────────────────────────────────────── ~150 行
│   index.ts           插件注册与配置（DSH 侧）
│   mobile/entry.ts    挂载 <PalmUI />
│
├─ L4 UI 层 ──────────────────────────────────────────── ~6,500 行  ★重写
│   ui/PalmUI.tsx            唯一入口（≤120）
│   ui/model/                AppModel 契约 + 路由 + 一次算好
│   ui/actions/              命令集合（按域分文件）
│   ui/screens/              9 个纯展示屏
│   ui/design/               12 个组件 + 语义 token
│   规则：不许 import 数据层/传输层；不许 useEffect
│
├─ L3 领域层 ─────────────────────────────────────────── ~9,000 行
│   mobile/data/            会话/工作区/设置/语音的读写（18 个域文件）
│   mobile/messages.ts      折叠与消息模型（2,640）
│   mobile/message-row/     行渲染模型（958）
│   mobile/mux.ts           事件流（990）
│   mobile/session-status.ts 状态投影
│
├─ L2 传输层 ─────────────────────────────────────────── ~4,600 行
│   mobile-api.ts           移动端 API（3,744）
│   api.ts                  共享类型与客户端
│   host/                   宿主侧 10 个域（2,124）  ★已拆
│
├─ L1 基础设施 ──────────────────────────────────────── ~3,300 行
│   pairing.ts (834) / updater.ts (804) / notify/ (1,018) / limits / security
│
└─ L0 资源与样式 ────────────────────────────────────── ~9,400 行
    mobile/styles/          42 个 CSS（真源）
    design/tokens.ts        明暗两套调色板
    mobile-styles.ts        ⚠ 生成副本，勿手改（有 freshness 测试）
```

**桌面端 `src/client`（4,556 行）是并列的第二个 UI**，与 L4 平级，共享 L0 的 token 契约
（`design/desktop-parity.ts` 锁死 11 对映射，现存 9 处差异）。

## 二、与五原则逐条对照

### ✅ 符合的部分

| 原则 | 证据 |
|---|---|
| **高内聚** | L2 宿主层已拆 10 个域（命令/目录/错误/性能/队列/证据/搜索/名单…），每域 87~517 行；`data/` 18 个域文件；`views/chat/` 62 模块分 4 子目录 |
| **低耦合** | 依赖单向向下；L4 两条硬约束（不许 import api/store、不许 useEffect）由断言守 |
| **可维护** | 2,666 条测试 + 视觉门禁 + 14 条架构断言 + 行数预算（只降不升）+ S0 行为指纹 |
| **高效** | 样式**构建期**拼接，零运行时（不引 Tailwind/CSS-in-JS）；移动端按路由分 chunk |

### 🟡 部分符合（有具体缺口）

| 原则 | 缺口 | 数字 |
|---|---|---|
| **简洁** | `src/mobile/` **顶层仍有 100 个散文件**（29,739 行），只有部分进了子目录 | 100 个文件 |
| **简洁** | `mobile-styles.ts` 是生成副本，却和真源一起计入代码量 | 9,378 行重复 |
| **低耦合** | `mobile-api.ts` 3,744 行仍是单文件，没按域拆 | 1 个文件 |
| **可扩展** | 新增一屏要动 4 处（route / model / actions / screen），没有"插槽"约定 | 无约定 |

### ❌ 不符合的部分

| 原则 | 问题 | 为什么算违反 |
|---|---|---|
| **可读性/简洁** | `messages.ts` 2,640 行 + `markdown.ts` 796 行 + `process-rows.ts` 497 行，都在 `mobile/` 顶层平铺 | 同层 100 个文件里挑不出"该看哪个" |
| **一致性** | 桌面与移动是两套 UI、两套样式实现，只共享 token | 同一个按钮改色要改两处 |

## 三、要达到"完全符合"，重写 UI 之外还要三件事

| # | 做什么 | 规模 | 收益 |
|---|---|---|---|
| **A** | 把 `mobile/` 顶层 100 个散文件按域收进子目录（`stream/` `render/` `session/` `platform/`），与 `views/chat/` 同款做法 | 1 天（纯搬迁 + 导入重算，已有脚本经验） | 找东西从 100 个文件降到 4 个入口 |
| **B** | `mobile-api.ts` 3,744 行按域拆成 `api/{sessions,chat,settings,market,voice}.ts` + 一个 facade | 2 天 | 与 `host/` 的 10 域对齐，一处改一处测 |
| **C** | 桌面端改用同一套语义 token（现有 9 处差异逐条消除） | 2 天 | 改色只改一处 |

---

## 四、结论：符合度自评

| 原则 | 现状 | 重写 UI 后 | 做完 A/B/C 后 |
|---|---|---|---|
| 简洁 | 60% | **85%** | 95% |
| 高效 | 90% | 90% | 90% |
| 高内聚 | 75% | **90%** | 95% |
| 低耦合 | 70% | **90%** | 92% |
| 可维护 | 85% | **92%** | 95% |
| 可扩展 | 65% | **85%** | 90% |

**一句话**：重写 UI 解决的是**第 4 层**（界面怎么组织）；项目整体架构的骨架
（L0–L3）**已经是分层清楚、单向依赖的**，主要遗留是 `mobile/` 顶层 100 个散文件
和 `mobile-api.ts` 这个 3,744 行的单文件。这两项与 UI 重写**互不阻塞**，可并行。
