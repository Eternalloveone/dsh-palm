## 二、真跑才暴露的问题（8 处）

全部是"信号说错话"性质，而不是判定逻辑算错——算法部分（浸泡判定、快进、哈希绑定、对齐比对）一次都没错。

| # | 问题 | 危害 | 现状 |
|---|---|---|---|
| 1 | 观察窗是**没有牙的闸**：`--after` 被解析后从未使用，打印的"1057 分钟"来自浸泡开始时间 | 一个看起来满足要求、实际量错对象的数字，会被人信任 | 已修：锚点改为 `next` 被设置的时刻（`state/next-tag.json`），无法确认即拒绝，跳过必须显式 `--after 0` |
| 2 | GitHub Release 把 rc 标成正式版 | 仓库页说 rc 是最新，npm 说 1.3.6 | 已修：仓库脚本对预发布版自动加 `--prerelease`；本机该 Release 已即时纠正 |
| 3 | 对齐检查未归一化 GitHub 标签的 `v` 前缀 | **永远为红的假警报**，真不一致反而被淹没 | 已修 + 回归钉住（"归一化不能把真差异一起抹掉"） |
| 4 | 渲染层把 `wait`/`warn` 一律印成 `SKIP` | 三种含义共用一个词，读者学会忽略这一列 | 已修：按状态如实渲染 |
| 5 | 残留的本地标签会被预检拦下 | 发布在预检阶段直接失败 | 已清理；预检现在**同时查远端** |
| 6 | `--check` 在"已上架但工作流尚未结束"时报 exit 1 | 若用作自动门禁，会在**成功**时报警 | 已修：0=已发布 / 1=失败 / 2=未完成 |
| 7 | `lib/release.mjs` 未导入 `spawnSync` 却当默认参数用 | 直接 ReferenceError | 已修（这次是 fail-loud，运气好） |
| 8 | Docker 引擎故障被 builder 误报成"源码不兼容" | 会让人去查一个完全正常的源码树 | 已修：失败时先探测引擎再决定说哪句 |

## 四、系统性结论与规矩

- 本次所有真问题都在**呈现层与闸的语义**，不在判定算法。
- 由此立规矩：**每条闸都必须配一条"故意失败"的测试**，断言它在该拒绝的时候真的拒绝。已按此补的回归包括：
  - 没有打点记录时，观察窗**绝不能**看起来像已满；
  - 归一化后，真差异仍必须失败；
  - 预发布版**绝不能**被提升为 `latest`。
- 24 小时门禁窗口是运营约束：想"今天发"，就必须当天新鲜跑完全量测试，否则毕业门会拒绝。

## 五、遗留建议

1. `--check` 的三态语义在真实失败/未完成场景各跑一次（可借 v1.3.5 那种历史失败样本）。
2. `palm release` 已在报告里识别"本版本已发布"，可考虑进一步提示"是否需要重新发布"。
3. 发布说明链路（AI 起草 → 人工确认 → CHANGELOG）目前正文仍取自 CHANGELOG，若要让草案直达 Release 正文需再走一步。
