# 0004 · 缓存收敛到一个内核 + 例外清单

- **状态**：已接受
- **日期**：2026-11-07
- **影响范围**：`src/mobile/**/*cache*.ts`、`src/mobile/kernels/cache*.ts`
- **相关**：`kernels/cache.ts`、`kernels/cache-policies.ts`、`kernels/cache-exceptions.ts`、
  `cache-adoption.test.ts`

## 背景

重构前有 **11 处各写各的缓存**，每处自己管：过期时间、容量上限、序列化、失效时机。

具体症状：

- **数字散落**：7 天、5 分钟、10 分钟、24 小时、80 行、220 KB、10 个会话……没有一个地方
  能回答"为什么是这个数"。
- **淘汰逻辑各写一遍**：有的按条数、有的按字节、有的完全不淘汰（长跑到配额满）。
- **落盘版本没人管**：行模型变了，旧缓存还在库里，读端要么报错要么画出错行。
- **失效时机漏掉**：写完不清窗，界面显示旧值（"刚删掉的工作区还在列表里"）。

## 决定

1. **一个内核**：`kernels/cache.ts` 的 `createCache({ ttlMs, maxEntries, maxBytes, sizeOf })`
   ——TTL / 条数 / 字节三套上限、`has()`、`fitByteBudget()`，加统一信封
   `wrapCache`/`unwrapCache`（版本不符整份作废）。
2. **一张策略表**：`kernels/cache-policies.ts` 把每份缓存的寿命/容量/落盘版本写在一起，
   **每条必须带 `why`**（这个数字为什么是这个数字）。
3. **例外必须登记**：`kernels/cache-exceptions.ts` 列明确不走内核的缓存，每条写清
   `why` 与 `freshnessFrom`。
4. **门禁**：`cache-adoption.test.ts` 断言——每个 `*cache*.ts` 要么用内核、要么在例外清单
   里；例外不许是过期条目；`why` 太短视为未登记。

现有两个例外：

| 模块 | 为什么 |
|---|---|
| `run-overview-cache.ts` | 存的是**渲染快照**，写穿式、没有"取数"，新鲜度由记录自带 `savedAt` 决定 |
| `history-cache.ts` | 落盘在 **IndexedDB**（大页、异步）；但 TTL/容量/页版本**已读策略表** |

## 代价

- **多一层封装**：简单场景（存一个值、读一个值）也要走 `createCache`，比手写 Map 啰嗦。
  换来的是"淘汰/裁剪/信封各只有一处"。
- **例外清单会被当成后门**：写个理由就能绕过内核。防线是"理由必须写 freshness 从哪来"
  ——如果说不清新鲜度依据，就说明这个缓存本来就没想清楚。
- **策略表里的 `why` 容易变成套话**：真正的判断标准是"改这个数字时，读 `why` 能不能知道
  会坏什么"。写不出来就说明当时没想清楚。
- **字节上限依赖 `sizeOf` 函数正确**：算错了就是超配额或过早淘汰，而这类错在小数据量下
  看不出来。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 引入成熟的缓存库（lru-cache 等） | 需求只有 TTL/条数/字节三样，自研 180 行够用；引库要多付体积与升级维护 |
| 所有缓存强制走内核，不许例外 | 会逼着把 IndexedDB 落盘硬塞进内存 Map 语义，或把写穿快照改成取数——两个都是**为了整齐而改坏行为** |
| 只做策略表，不做内核 | 数字统一了但实现还是 11 份，淘汰逻辑照样各写各的 |
