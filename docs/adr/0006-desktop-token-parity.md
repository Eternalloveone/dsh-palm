# 0006 · 桌面设计令牌与移动端同源

- **状态**：提议（W5-4 未完成）
- **日期**：2026-11-07
- **影响范围**：`src/mobile/**/*.ts`（内联样式）、桌面 Web UI 的 `--palm-*` 变量
- **相关**：`docs/UI.md`

## 背景

同一个产品有桌面 Web UI 与移动端两个界面，配色与间距**各写一套**：

- 移动端把颜色写在内联样式对象里（`mobile-styles.ts` 与各视图的 style 对象）
- 桌面端用 `--palm-*` CSS 变量
- 结果是"同一个品牌色"在两个端有两个值，改一次要改两处，且**没有断言能发现不一致**

## 决定（提案）

1. 移动端的设计令牌收敛进 `design/tokens.ts`（单一来源），23 个 `--palm-*` 变量映射到它。
2. 断言：两端的同名令牌值必须相等；移动端不许再出现裸色值（`#rrggbb`）与裸间距数字。
3. 迁移分两步：**先建令牌并让新代码用**，再逐屏替换旧值（每替换一屏跑一次视觉门禁）。

## 代价（预期）

- **视觉回归风险**：替换色值会改变像素，视觉门禁的阈值必须逐屏确认，不能一把梭。
- **内联样式与 CSS 变量是两种机制**：令牌层要同时服务"JS 对象"和"CSS 变量"两个消费方，
  中间需要一个生成/映射步骤，这个步骤本身就是新的维护点。
- **23 个变量里可能有些桌面端已经在用、移动端并不需要**：硬统一会造出一堆没人用的令牌。
  更稳的做法是**只统一两端都用到的**，其余留在各自端。

## 当前状态（诚实记录）

W5-4 **未开始实施**。本轮（W5-5 治理收口）只把它写进 ADR，让"两端不同源"这件事有据可查，
避免下次又当成新发现。真正落地需要：令牌表 + 断言 + 逐屏迁移，估 3 天。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 移动端直接读桌面 CSS 变量 | 移动端样式是内联对象，拿不到 CSS 变量值（除非运行时读 computed style，成本高且闪） |
| 各端保持独立，只在大版本前人工对一次 | 已验证会漂移；而且没人会记得"大版本前要对一次" |
