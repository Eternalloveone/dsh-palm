# 0005 · 架构断言与预算进 CI，预算只降不升

- **状态**：已接受
- **日期**：2026-11-07
- **影响范围**：`src/mobile/architecture.test.ts`、`src/mobile/quality-budget.ts`、CI
- **相关**：`tools/health-check.mjs`、`docs/MOBILE-VISUAL-GATE.md`

## 背景

重构期间反复出现同一类退化：

- 拆出去的逻辑**又被搬回视图**（因为"就在手边方便")；
- 视图文件**慢慢长回去**（每次加几十行，单次都合理）；
- 视图重新开始**直接调 `api.ts`** 取数（绕过分层）。

靠 code review 拦不住：一次加 40 行看起来完全正常，十次就是 400 行。这类问题必须由**机器**
在每次提交时判，不能靠人记。

## 决定

1. **架构断言**（`architecture.test.ts`，当前 12 条）：
   - 依赖方向：内核不许 import 视图/数据；`views/` 不许直接 import `api.ts` 的取数函数
   - 不留新环：`tools/dep-cycles.mjs` 的环数量有基线，多一条就红
   - 单一实现：某些共享 helper 只能有一处定义
   - 文件行数预算：`ChatView` / `SettingsView` / `SessionListView` / `App` … 每个都有上限
2. **预算只降不升**：改代码让文件变短了，就**顺手把预算调低**；永远不许为了过关把预算调高。
3. **质量预算**（`quality-budget.ts`）：`viewDataImports` 这类计数指标同样只降不升，且
   **预算不许虚高**——测试会断言"实测值 + 5% ≥ 预算"，防止预算写大了形同虚设。
4. **一键体检**：`node tools/health-check.mjs` 串起 typecheck → build → test → 视觉门禁。

## 代价

- **改不动的地方要写清楚**：`ChatView` 的最终目标是 ≤800 行，但翻页/滚动与 state 咬在一起，
  当前仍未达到。**预算只降不升**意味着这个数字会一直提醒"还欠着"，而不是假装完成。
- **预算会阻碍正当的重构**：拆文件时行数短暂上升（import 变多）就会红。处理方式是把同域的
  import 合并、把纯函数挪走，**而不是调高预算**——这个约束逼出了更好的拆法，但也确实费时。
- **断言会误判**：例如"用没用内核"曾用路径子串判断，导致读了策略表就被当成用了内核。
  写断言的通用教训：**判据要看本体，不要看附近有什么字符串**。
- **12 条这个数字不是目标**：目标计划里写的是 8 条，实际长出 12 条。**数量本身没有意义**，
  有意义的是每条都在拦一类真实发生过的退化。

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 只靠 review 与规矩 | 已验证失败：这类退化单次都"看起来合理" |
| 用 ESLint 自定义规则 | 行数预算、环检查、跨文件计数用 ESLint 写更绕；vitest 里直接读文件更直白 |
| 引入依赖图工具（dependency-cruiser 等） | 只需要"环数量"和几条方向约束，`dep-cycles.mjs` 百来行够了 |
