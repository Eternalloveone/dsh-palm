# 0001 · 薄表现层 + 六个内核 + 单一契约

- **状态**：已接受
- **日期**：2026-11-07
- **影响范围**：`packages/dsh-palm/src/mobile/**`
- **相关**：`src/mobile/kernels/`、`src/mobile/architecture.test.ts`

## 背景

重构前移动端的 `ChatView` 一个文件 **5,000+ 行**（含样式与状态），`App.tsx` 也在千行级。
典型症状：

- **同一件事三处实现**：滚动锚点、翻页去重、未读判定各写各的，改一处另外两处不知道。
- **界面乱跳**：进会话先空壳再一条条长出来；底部弹层打开时整页被顶一下（真机才复现）。
- **改不动**：想给聊天页加一个"跳到某轮"，要在 5,000 行里找散落在 effect、ref、闭包里的状态。
- **测试写不出来**：纯逻辑和 DOM 缠在一起，只有 e2e 能测，而 e2e 跑一次要真机。

根因不是"代码写得差"，是**没有分层**：数据获取、状态派生、呈现、交互副作用全在一个文件里，
谁也说不清一行代码属于哪一层。

## 决定

三层，依赖方向只能向下：

```
视图（views/）      只管画：把 props 变 DOM，不取数、不算派生
   ↓
内核（kernels/）    六个纯逻辑单元，无 React、无 DOM：
                    Identity / Intent / Presence / Clock / Viewport / Cache
   ↓
数据（data/）       取数与缓存，按域分门面（session/workspace/settings/...）
```

**单一契约**：每个内核对外只暴露一个 `create...()` 工厂 + 少量纯函数；视图只能通过它拿状态，
不能自己发明第二套。

配套门禁（见 [0005](0005-architecture-gates.md)）：

- `views/` 不许直接 import `api.ts` 的取数函数（只允许 `import type`）
- 内核不许 import `views/` 或 `data/`
- 每个视图文件有行数预算，**只降不升**

## 代价

- **前期更慢**：把 5,000 行拆开比重写一遍还费劲，因为要先弄清哪些逻辑其实是重复的。
- **多了一层间接**：改一个行为常常要动"内核 + 视图"两处，纯改样式反而变绕。
- **拆得不彻底的地方更糟**：视图里残留的 state/effect 与翻页、滚动咬在一起时，硬拆的收益
  低于风险——这类地方暂时保留，代价是"这里不符合架构"要一直记着（已记在进度表偏差里）。
- **六个内核这个数字不是教条**：如果发现第七个真的独立，就该加；如果两个其实是一件事，
  就该并。**数目本身没有价值，边界清楚才有。**

## 备选方案

| 方案 | 为什么不选 |
|---|---|
| 直接重写一个新 UI，旧的一起删 | 移动端有配对、CSP、断线重连等一堆真机才暴露的约束，重写会把这些坑再踩一遍 |
| 只做"组件库化"（抽 Button/Card 等） | 症状是状态与数据流，不是视觉；抽组件不解决"同一件事三处实现" |
| 引入 Redux/Zustand 之类统一状态 | 问题不是缺状态容器，是缺少"这段逻辑属于哪一层"的划分；换库只是把混乱搬个家 |
