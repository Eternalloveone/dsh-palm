# 手机端测试模型：旅程 × 不变式

> 这份文档回答一个问题：**"测试集漏了什么"能不能算出来**，而不是靠回忆。
>
> 相关代码：`tools/mobile-scenarios/model.mjs`（模型与登记表）、`coverage.mjs`（算覆盖）、`scenarios/*.mjs`（场景）。

## 一、为什么不是"想到一个补一个"

补场景的最常见做法是"用户报一个 bug → 写一个场景"。这样做永远收敛不了，因为：
① 只有被撞到的问题才会被测；② 没人知道还剩多少没撞到；③ 新场景之间没有关系，说不出"够不够"。

这里换成两维模型：**用户想做成什么（旅程）× 做这件事时必须守住什么（不变式）**。
每个场景必须声明自己守哪几格 —— 于是"缺口"是**算出来**的。

## 二、模型

### 旅程（用户视角，按"要办成的事"切）

| | 旅程 |
|---|---|
| J1 | 打开与首页（冷启动、首页信息、运行中入口） |
| J2 | 找到目标（列表、搜索、切会话、切工作区） |
| J3 | 读内容（首屏、滚动、翻历史、长会话、选中复制） |
| J4 | 写与发（输入、草稿、附件、排队、停止、发送失败） |
| J5 | 等与看（过程条、秒表、交付卡、命令卡、审批、子代理、绿点） |
| J6 | 结果与文件（图片/文件预览、链接、路径复制） |
| J7 | 管会话（新建、重命名、归档、删除、模型/权限切换） |
| J8 | 环境变化（弱网、断流、后台、换设备、旋转、字号、主题） |
| J9 | 出错与恢复（打不开、宿主 500、超时、限流、重试） |

### 不变式（界面底线，与 `docs/MOBILE-RENDERING.md` 同一套编号）

I1 单一来源 · I2 位置身份 · I3 单调 · I4 一次成型 · I5 缓存优先 · I6 阶段显式 · I9 失败可举证
另加：S 状态机一致 · D 数据一致 · U 可操作 · P 性能预算

### 必守格

不是 9×11 全都要（"翻历史"和"一次成型"基本无关），而是每条旅程逐格声明必须守什么，写在 `model.mjs` 的 `REQUIRED`。
覆盖率按**必守格**算；全矩阵只用来展示信息量。

## 三、怎么用

```powershell
node tools/mobile-scenarios/coverage.mjs            # 打印矩阵 + 缺口
node tools/mobile-scenarios/coverage.mjs --strict   # 有空缺就退出码 1（给门禁用）
```

矩阵里数字＝守着该格的场景数，`·`＝空。缺口分两类：

| 类型 | 处理 |
|---|---|
| **真缺口** | 补场景（先看格子，再写代码，不从"想到什么"出发） |
| **已接受** | 写进 `ACCEPTED_GAPS` 并注明原因，缺口味"已知"，不是"不知道" |

## 五、加场景的规矩

1. 先在矩阵里指认格子；指不出来就别加。
2. 场景文件头写清：**守哪几格** + **判据为什么这么写**（踩过的坑也写在旁边）。
3. 同步 `model.mjs` 的 `SCENARIO_CELLS` —— 没登记 `coverage.mjs` 会报错。
4. 只读场景**绝不新建会话、绝不发消息**；会发消息的一律 `manual` + 专用测试会话。
