## 每个目标做了什么

### (1) 索引表加结构坐标 — 完成

- `docs` 表新增 `turn` / `step`，`SEARCH_INDEX_VERSION` 升到 5
- 搜索命中回 `turn` / `step`（真机实测 `{"turn":256,"step":1,"role":"assistant"}`）
- **修掉一个真 bug**：版本升级时只 `DELETE FROM docs`，而 `CREATE TABLE IF NOT EXISTS` 对已存在的表什么都不做 —— `meta.index_version` 写着 5、表里却没有 `turn` 列，坐标永远写不进去。改成 `DROP + 按 SCHEMA 重建`，加回归测试
- 真机库实测：8514 行，其中 4706 行带坐标

### (2) 定位层重写 — **部分达成**

| 子项 | 状态 |
|---|---|
| 意图层保留 | ✅ `locate-intent.ts` 未动 |
| 图寻路 | ✅ `locate-anchor.ts`（15 条测试）+ 第三锚点 `turnStepRowIndex` 已接入 |
| 纯函数状态机 | ✅ 无状态版 `decideMiss`（8 条单测 + 32 组合穷举）已接入 ChatView 决策段 |
| 60 行执行器 | **用户裁决关闭**：实测 208 行有效代码（135 行锚点解析，逐条对应真机形态），用户 2026-11-12 明确接受现状 |
| 替换 508 行 | ❌ 只替换了决策段（约 22 行） |
| 13 个状态载体 | **部分** 15 → 11（五个目标字段合并为一个对象） |

**有状态版 `stepLocate` 回滚了**（16 条测试留在库里）：它要调用方持有 `LocatePhase`，而那个状态在 ChatView 里活不过一次重挂载 —— 实测 53 次进状态机每次读到的都是 `idle`。试过 `useSessionRef` / 普通 `useRef` / 渲染期幂等三种存法都不行。

**真正的解法是不该有存活状态**：决定下一步做什么所需的事实（翻到第几页、跳过没、有没有在飞）本来都在调用方已有的 ref 里，于是补了无状态版 `decideMiss`，与原来的 if 链逐条等价，但组件重挂载多少次都不影响。

**另外两件真实收获**：
- 删掉 `findAnchor()` 20 行重复锚点解析（它和 `run()` 里的判据不一致）
- 修 `use-chat-history.ts` 一个真 bug：三条失败路径的 `pendingRef.current = false` 都排在 `if (!isCurrent()) return` 之后，「请求失败 + 此刻已不 current」就让 pending 永久为 true、后续翻页全排队

### 那 307 行为什么减不下来（实测数据）

用 `count-locate-lines.mjs` 精确统计落点 effect：

| 项 | 行数 |
|---|---|
| 总行数 | 307 |
| **有效代码** | **208** |
| 注释 | 99（32%） |
| 空行 | 0 |

分段：

| 段 | 行数 | 内容 |
|---|---|---|
| 入口守卫 | 27 | `focusMsgId` 空 / 已滚过 / 无 target / 无容器 |
| **`run` 锚点解析** | **135** | messageEl → partEl → marks → stepScope → pool → markEl，加两处折叠展开重试 |
| verify | 33 | 读回真实几何 + `judgeLanding` |
| settle | 49 | 三次 220ms 校准 + `ensureMarkInView` |
| 补偿 | 37 | 只补差额、重试 rAF |
| retry | 26 | 等渲染行出现（50ms × 120） |

**208 行有效代码里 135 行是锚点解析** —— 那不是冗余，是「一行里多处命中 / 命中在折叠里 / 命中在合并卡的第 N 步 / 长消息折叠在『展开全文』后面」这些真机形态的逐条对策。注释占 32%，记的全是「越补越偏」「高亮了但看不见」这类现场结论。

所以「60 行执行器」在这个组件里做不到 —— **不是没重构，是那 208 行每一段都在处理一个具体的坑**。要减只能删功能（比如放弃「展开折叠再定位」），那是产品决定。
