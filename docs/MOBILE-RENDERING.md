# 手机端渲染稳定性架构（dsh-palm）

> 这份文档回答一个问题：**怎么保证"每个页面都稳定渲染"，而不是一页一页去救火。**
> 2026-10-30 一天里连续修了 6 个"闪/跳/重复"问题（折叠按钮被裁、进会话整屏闪、
> 同一轮多张过程卡、排队条重复与残留、运行中页逐项长出来），它们不是 6 个 bug，
> 是**同一类结构缺陷**的 6 次发作。这份文档把那一类缺陷写成规则。

## 一、缺陷的统一形状

所有"不稳定"的现场都满足同一句话：

> **同一个显示单元，在不同的时刻/不同的来源，拥有不同的身份。**

身份一变，React 就卸载重挂（闪），列表就重排（跳），同一实体就出现两份（重复）。
所以稳定性的本质不是"少 setState"，而是**身份定义**。

## 二、六条不变式（页面必须逐条满足）

| # | 不变式 | 违反时的现场 | 落地要求 |
|---|---|---|---|
| **I1** | **单一真源**：一个页面只从一个 store 读；写入只有一条路径 | 同一个数字两处各算一遍，互相打脸 | 页面内所有数据经 `apply(channel, payload)` 入 store |
| **I2** | **位置身份**：实体 key 由它在数据里的位置决定（`sessionId` / `turn+step` / `seq`），**永不由生产者分配的 id 决定** | 三套 id 各不同 → 同一行存成两条 | 每个实体声明一个 `identity(entity)`，全局唯一实现 |
| **I3** | **单调**：列表只增不减、版本只升不降（`maxSeq` / `queueRevision` / `queueToken` / `snapshotSeq`）；低水位数据一律丢弃 | 旧快照把新数据盖回去 | store 保存高水位，写入前比较 |
| **I4** | **一次成型**：进入页面 = 一次请求 → 一次提交 → 一次定位；**首屏之后不再往列表里插内容**（更早的页只在用户上滑时加载） | 进会话补页把列表往上一顶 → 跳 | 首屏一次取够（聊天页 120 行）；补页只在手势触发时 |
| **I5** | **缓存先画**：上次稳定态先铺（带 TTL），后台对齐只做增量替换；**失败不清空** | 每次进入都先空壳再填充 | 页面级快照缓存 + TTL + 合并语义 |
| **I6** | **阶段显式**：`entering` / `live` / `idle` 三阶段，每阶段的渲染规则写死（是否钉底、是否播动画、是否允许回退） | "有时闪有时不闪"，无法复现 | 页面上声明 phase，渲染分支只认 phase |

两个推论（今天都踩过）：

- **流式行的身份必须在流式过程中不变**（`turn+step` 已知就按它；未分步时按"本轮的未分步行"，**不能按 `seq`**，否则每个 chunk 换身份）。
- **只在 `pending` 行播入场动画**：历史行播动画等于把"重挂"放大成"整屏闪"。

## 三、执行机制（靠闸门，不靠自觉）

| 层 | 机制 | 位置 |
|---|---|---|
| 数据层 | `view-core`：`createViewStore({ identity, merge, watermark, cache })`，I1/I2/I3/I5/I6 由它保证 | 待建（本文件配套） |
| 闸门 | `tools/mobile-render-audit/`：对每个页面自动跑 4 条不变式（见下），失败即红 | 已入库 |

| 评审 | 新增页面必须声明 `identity / merge / cache / phase` 四项，缺一不予合入 | 本文件 §二 |

### 入场瞬时（50ms 一帧）另有一条判据

上面 4 条是**页面级**稳定性的度量；「同一轮两张过程卡」这种问题只存在一瞬间
（入场那几百毫秒，或流式追加期间），必须换节奏抓：

`node tools/mobile-render-audit/stress-entry.mjs`（`pnpm verify:render:stress`）

- 每 **50ms** 采一帧，连续 40 帧；
- 判据：① 同一 `turn` 不允许同时挂 2 张过程卡；② 不允许重复 `data-message-id`；
- 两种现场都跑：**静置会话**（缓存 + 尾页两个生产者重叠）与**在跑会话**
  （缓存 + 尾页 + 实时帧三个生产者同时有数据 —— 当初 turn 147 两张卡就是这种）。

实测（2026-10-30 收尾）：**静置 6 会话 × 2 次进入 + 在跑 3 次进入，共 720 帧采样，违规 0**。

> 诚实备注：把 `rowIdentity` 临时改回旧实现（`(turn,step)` 否则 `row.id`）再跑同一套高压，
> **违规同样是 0** —— 说明本次无法用这套复现证明「身份修复单独解决了它」。最可能的
> 真实功臣是同时上线的两件事：**入场只提交一次**（I4）与**合并入口统一补轮号**
> （`normalizeTranscriptRows`）。身份改成位置仍然是对的（它是 I2 的实现），但不再被
> 当作唯一解释。这条判据现在被永久守着，将来回退会立刻变红。

### 自动审计的 4 条判据

对**每一个页面**（首页 / 会话列表 / 聊天 / 运行中 / 设置 / 配对…），在真宿主 + 真浏览器里：

1. **行数单调**：进入后的前 3 秒，可见单元数量**不允许减少**（缓存→网络、翻页都不许塌缩）；
2. **身份不重复**：同一 `identity` 不允许同时出现两个 DOM 节点（React key 唯一性）；
3. **首帧完整率**：150ms 时的"完整单元数 / 稳定态单元数"应 ≥ 80%（缓存命中时应为 100%）；
4. **离底为 0**：列表类页面的滚动位置在稳定后必须贴在最新一端（`gap ≤ 2px`）。

## 四点五、根因定位与回归闸门（2026-10-30 收尾）

### 已被 A/B 证实的根因：**卡片单位是「行」，不是「轮」**

中途插话会把一轮拆成两行（step 1 … 用户插话 … step 40）。渲染层如果按「行」决定
画不画卡片，这两行就会各画一张 —— 卡片里是**同一批工具**，看起来就是"同一轮两张过程卡"。

A/B 证据（同一台宿主、同一份数据）：

| 版本 | 生产入口用例 `turn 147 形状` | 说明 |
|---|---|---|
| 关闭按轮归属（`return out`） | **失败：带工具的行 = 2** | 两行各画一张卡 |
| 当前实现 | 通过：带工具的行 = 1 | 卡按轮归属，正文与工具都不丢 |

> 用例必须从**生产入口** `coalesceTurnMessages` 进去。原先那 3 条只直接调
> `mergeProcessCardsByTurn`，把接线换成 `return out` 时照样全绿 —— 这是本轮发现的
> 测试缺口，已补（`messages.test.ts` 的「回归闸门」组）。

### 未被证实、也不再归因于身份的一部分

- 「入场瞬间缓存页与实时页各存一份」在结构上可能，但把 `rowIdentity` **连同**归一化
  一起退回旧实现后，50ms 高压采样（720 帧）与拖慢尾页 4 秒的确定性探针（100 帧）
  **都仍是 0 违规** —— 现在无法复现，因此**不把它当作已证实的根因**；
  它由 `stress-entry.mjs` 长期守着，回退即红。

### 一条被数据否决的改动（值得记下来）

想放宽重复上报判据到「同轮两行都带过程就上报」，被现有用例当场拦下：

> `同轮、正文短、工具不同、seq 不重叠 → 不算重复（多步正常合并就是这形状）`

插话后的正常轮次正好是"两行都带过程"，这一放宽会让每轮都误报，于是**撤销**，
上报判据保持原样（工具重叠 / seq 重叠 / 正文相同）。

## 四点六、交付卡（本轮产出）也必须一次成型

**现象**：点进会话时正文先到，交付卡随后一张张"长出来"（有的还会先给一版猜的、几秒后被正式版替换）。

**根因**：卡片不在首屏载荷里 —— 首屏只有 29 行的尾窗，跨窗之外的回合没有 `turn/end`，
只能由 `cardRecovery` 事后回读日志再补。

**修法（两层，都不拖慢首屏）**：

| 层 | 做法 |
|---|---|
| 记忆库 | 补到的真卡按「会话 × 轮」记住（`chat-snapshot` 的 `turnReports`）；**再次进这一场**就在同一次提交里带上卡 |
| 兜底 | 第一次进（无记忆）仍交给 `cardRecovery` 后台补；补到即记忆，所以"长出来"每场只发生一次 |

**实测**（同一会话，先冷后热）：

| 进入 | 卡片首现 | 800ms 后还在增加 |
|---|---|---|
| 第一次（无记忆） | 随正文之后补（原有行为） | 是 |
| 第二次（有记忆） | **100ms，与正文同一次提交** | **否** |

## 四点七、正在跑的回合绝不能有「已完成」卡

**现象**（2026-10-30 真机截图）：底部明明写着"输出中…"，上面那张过程卡却是
✅ 已完成 / 用时 1分45秒 / 本轮产出 2 个文件。

**根因**：卡片状态是从**工具状态**推的，不是从"这一轮有没有收工"来的。

- 猜卡（`ensureTurnTails`）与补卡回读（`missingTurnReports`）都只看
  "还有没有 running 的工具"；
- 但一轮完全可能**工具都跑完、模型还在输出正文** —— 此时 `turn/end` 尚未出现，
  工具状态却已全绿，于是被判定为"收工"，凭空造出一张已完成卡。

**架构修法**：把"哪一轮在跑"从推断改为**显式输入**（唯一真源 = 实时流）。

| 改动 | 内容 |
|---|---|
| `ensureTurnTails(rows, openTurn?)` | `openTurn` 那一轮不猜卡 |
| `missingTurnReports(rows, openTurn?)` | `openTurn` 那一轮不算"缺卡"，不回读（回读也会造出已完成卡） |
| `renderRows(rows, allowGuessedTails, openTurn?)` | 透传 |
| `ChatView` | `openTurn = turnLive ? (runningTurn ?? 最新轮) : undefined`，随每次提交传入 |

判据从此只有一条：**`turn/end` 出现了才算收工**；工具状态只描述工具，不描述回合。

**回归闸门**（`messages.test.ts`）：

- 没有 `turn/end`、工具已全绿 → 历史视角算缺卡；`openTurn` 视角**不算缺卡**；
- 收工后（`openTurn` 消失）照常补卡；
- 历史轮次不受影响（只有"正在跑的那一轮"被排除）。

**真机验证**：跑着的时候连续采样（500ms × 60 帧），"底部在跑 且 有卡写着已完成" **0 帧**。

## 四点八、首屏请求就把交付卡（turn/end）一并带回来

**目标**：第一次进会话也要"一次成型"，不靠几秒后的回读补卡。

**做法（宿主侧，仍是一次请求）**：

| 环节 | 做法 |
|---|---|
| 尾窗字节 | 首屏读尾部放开到 **2 MB**（原来默认窗口只够几十帧 → 折出 29 行，剩下靠进会话后再补页） |
| 帧预算 | `maxRows × 12` 帧（实测 ~12 帧折 1 个可见行） |
| 缺卡则加宽 | 折完后若发现"有工具行却没有卡的历史回合"，再读一次 `BOUNDARY_TAIL_FRAMES` 宽窗把它们的 `turn/end` 带回来重折 —— **只在需要时**多读一次本地文件 |
| 客户端缓存 | 缓存改为"画面稳定 400ms 后写完整一屏"（含卡片），下次进入首帧就是完整画面 |

**实测（628d 会话，冷/热各一次，50ms 采样 × 3 秒）**：

| 指标 | 结果 |
|---|---|
| 3 秒内出现过的状态 | 只有两种：`0/0`（加载中）→ **`7 卡 / 67 行`**（一次提交完成） |
| 二次进入首帧 | 同样直接是 `7 卡 / 67 行`（100ms 内） |
| 800ms 之后是否还在增加 | **否** |
| "加载更早"是否仍可用 | 可用：拉回顶部后 67 → 93 行 |

## 四点九、进会话不再"重新加载"：key 也必须按位置

**现象**：一进会话，正文和交付卡有时会像"重新加载"一遍（内容先出现、随后整块换掉）。

**根因**：React 的 key 落回了 `row.id`。

- 没有 `turn/step` 的行（用户消息、系统行、流式早期行）以前 `key = id`；
- 而缓存 / 实时帧 / 网络页三套 id 各不相同 —— 网络页一落地，这些行 key 全变，
  React 卸载重挂，屏幕上就是"整屏重渲染一次"（动画重播、展开的折叠被收起）。

**修法**：`messageKey` 与合并身份用同一条位置规则 ——
`(turn, step)` → `seq` → `startSeq` → 最后才 `id`。
同一位置的行，无论来自哪个生产者，key 都不变，React 只更新内容、不卸载节点。

**实测（628d，缓存命中后进入，节点存活率）**：

| 指标 | 结果 |
|---|---|
| 首帧行数 / 打标记节点 | 67 / 67 |
| 4 秒后仍然存活的首帧节点 | **67 / 67 = 100%** |
| 结论 | 只做增量更新，没有整屏重挂 |

> 边界：本轮测的是"缓存 → 网络页"这条路径。**实时行 → 网络页**（会话正在跑时进入）
> 用的是同一个 key 函数，理论上同样稳定，但没能在本轮端到端 A/B 出来，已在
> 单测层覆盖身份规则。

## 四点十、首屏窗口自适应（弱设备保护）

首屏读尾部现在是 **2 MB**（一次尽量拿全）。为了避免超长会话在弱设备上变慢，
客户端记录最近 3 次"进会话多久出内容"：

| 上次平均耗时 | 首屏尾窗 |
|---|---|
| ≤ 1200ms | **2 MB**（一次拿全） |
| > 1200ms | **512 KB**（先快出内容，剩下的靠补页） |

窗口由客户端在 `mobile.logTail` 请求里带上 `windowBytes`，宿主夹在 128 KB ~ 4 MB。

## 四点十一、"在跑"的小绿点也必须由证据点亮

**现象**：会话明明在跑，首页/列表上的"运行中"小点一直是灰的。

**根因**：点亮逻辑只认"宿主 running 集合里出现过"的会话，而实测那份集合会**漏报**
（正在跑的会话不在里面，它靠 `session/status` 帧维护，而真机上这类帧几乎不发）。

**修法（判据仍是证据，不是猜）**：

| 手段 | 内容 |
|---|---|
| 周期核对 | 页面可见时每 5 秒核对一次；`visibilitychange` 回前台立刻核对 |
| 漏报兜底 | 对"最近 10 分钟内活跃的前 8 行"直接按**尾页最后一条边界**核实（`turn/start` = 在跑） |
| 熄灯不变 | 宿主说没在跑 → 立刻灭灯（这条一直是对的） |

**实测**：停在列表页不动，另一个会话起长回合后 **1 秒内**绿点亮起。

## 四点十二、压测与验收数字（2026-10-31 复测）

| 项 | 命令 | 结果 |
|---|---|---|
| 逐页渲染审计 | `node tools/mobile-render-audit/run.mjs` | 5 页：4 PASS + 1 SKIP（设置入口选择器待补），行数回退 0、身份重复 0、离底 0px |
| 入场高压（50ms 采样） | `node tools/mobile-render-audit/stress-entry.mjs` | 600 帧（静置 6 会话 + 在跑 3 次进入），**违规 0** |
| 整屏重挂检测 | `probe-remount.mjs` | 首帧 67 个节点，4 秒后存活 **67/67 = 100%** |
| 进会话耗时 | 冷 / 热 | 冷（首次、无缓存）**1.7s**；热（缓存命中）**100ms**，两者都是 67 行同一画面 |

> 首屏 2 MB + 缺卡加宽让"第一次进"变慢（1.7s），换来的是首屏一次成型；
> 之后每次进入走缓存 100ms。若嫌首次慢，可把 `TAIL_WINDOW_WIDE_BYTES` 调小。

## 四点十三、进会话"历史全在、卡片不再重画"（对齐桌面端）

| 环节 | 做法 |
|---|---|
| 缓存深度 | 每会话最多 **400 行**（含交付卡）。绝大多数会话一次就够，"全都在"由本地缓存提供 |
| 对象复用 | 合并时若两行"画出来一样"（`sameRenderedRow`：kind/turn/step/seq/pending/正文/思考/工具/交付物/flow 全等），**返回旧对象** —— React 跳过重渲染，卡片不会被重画 |
| 尾窗策略 | 默认 **512 KB**（实测 2 MB 1.7s / 512 KB 0.7s）；只有实测 ≤800ms 才放宽到 2 MB |

**实测**（首帧 vs 4 秒后）：

| 指标 | 结果 |
|---|---|
| 行数 / 卡片数 | 首帧 24 行 / 7 卡 → 4 秒后 **完全相同** |
| 首帧 DOM 节点存活 | **24 / 24** |
| 卡片文案被改写 | **0 / 7** |
