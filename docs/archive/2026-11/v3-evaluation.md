# v3（展示层一等化）评估

> 结论：**方案成立，能实现"构建期多皮肤 + 视图可换"，但"皮肤自由"要先把一个词拆开。**
> 按当前代码判断，v3 有 2 处判断与事实不符、1 处低估、1 处高估；工期从 16.5 天调为 **20 天**。
> 末尾那个拍板问题：**建议直接替换默认，不长期并存。**

---

## 一、"皮肤自由"是三档，v3 只交付其中一档

| 档 | 含义 | 成本 | v3 是否交付 |
|---|---|---|---|
| **A 构建期多选一** | 一条 profile 切皮肤/视图，发布时确定 | 低（当前 CSS 全是构建期生成） | ✅ |
| **B 运行时换 token** | 手机上点一下换配色，结构不动 | **低**（见下） | ❌ 但**建议补上** |
| **C 运行时换结构** | 换的不只是颜色，而是视图实现 | 高 | ❌ 明确不做 |

### 关键修正：v3 把 B 档错判成"违反规则 5"

规则 5 是「**样式零运行时**」——指不许在 JS 里算样式（CSS-in-JS、style 对象）。

**而"只换 token"的换肤不需要运行时算样式**：所有皮肤的 `tokens.<skin>.css` 构建期全部打进包，
运行时只切一个属性（`<html data-skin="x">`），CSS 变量自动生效，**零 JS 样式计算、零新增运行时**。

代价只有三样，都可量化：

| 代价 | 量级 | 对策 |
|---|---|---|
| 包体积 | 每套皮肤约 3–5 KB（纯变量声明） | 3 套以内可接受 |
| 断言复杂度 | "包内只有一份 overrides" 失效 | 改成"每套皮肤恰好一份，命名 `overrides.<skin>.css`" |
| 验收面 | 9 屏 × N 套皮肤截屏 | 用现有视觉门禁跑矩阵 |

**所以："皮肤自由"如果指的是用户能在手机上换配色，v3 现在的判断是过严的**，成本比它想的低得多。
真正贵的只有 C 档（换结构），那档确实不该做。

## 二、两处与当前代码不符

| v3 的写法 | 实测 | 影响 |
|---|---|---|
| "⚠️ P-V 先确认仓库有没有现成 headless 截屏能力；没有就只做人工签核" | **已有**：`tools/mobile-visual/`（Playwright + baseline + 逐屏 diff + 阈值），且今天刚修好"一次性引导层盖住整屏导致全线误报"的问题 | P-V 的 0.5 天**够用**，不需要"人工签核"降级；但它有已知抖动（预览服务器与 build 抢资源），要串行跑 |
| "用现有 zod（已是依赖）" | ✅ 属实：`zod ^4.6.7` 在 dependencies | 可以放心用，不引新包 |

## 三、一处低估：P0a 断言引擎换成模块图

v3 给 1.0 天。**按代码实际，这是低估。**

现在 14 条断言是 `readFileSync` + 正则，要换成 TS Compiler API，得处理：

| 难处理 | 为什么 |
|---|---|
| 别名解析 | 需要读 tsconfig `paths`，不能硬编码 |
| `export *` 展开链 | 要递归展开 barrel，还要防环 |
| 动态 `import()` 字面量 | 只能静态解析字面量，变量拼路径无法判 |
| `import type` 区分 | 类型导入不构成运行时依赖，判错会把合法写法判红 |
| barrel 归一 | 同一模块经不同路径引用，要归一成同一节点 |
| **等价性验收** | "14 条新旧判定完全等价"要求在**同一份代码**上跑两套引擎比对，不是"新引擎通过了就行" |

**实际 2.0 天更稳**（含等价性比对脚本）。

## 四、一处高估：双轨期 golden 的"三不"

v3 说 golden "不计入预算、不进断言扫描、不进产物"。前两条合理，**第三条有坑**：

golden 是 `.tsx` 源码，只要还被 `tsconfig` 包含，就参与类型检查和测试运行；
"不进产物"要靠构建入口排除，而**排除规则写错就会把新视图一起排掉**（A 步我们刚被类似问题咬过：
测试路径写死、导入重写漏项）。

建议加一条验收：**golden 目录被删除后，包体积与 chunk 清单必须与删除前完全一致**——
这才能证明它真的没进产物，而不是"以为没进"。

## 六、拍板：新皮肤直接替换默认

**同意 v3 的倾向，理由比它写的更硬：**

1. **"包内只有一份 overrides" 这条断言是双轨并存的死穴**。两套并存时，加载顺序一变就是整屏视觉回归，
   而这类回归**只在真机上偶发**，测试环境复现不了（我们今天已经踩过一次类似的：引导层盖屏，headless 正常、真机异常）。
2. **双轨会变成第二套产品**。旧 UI 会继续接需求（"先改旧的快"），半年后 golden 变成主力。
3. **视觉基线可以留，代码不能留**。删掉 `golden/`，但把 9 屏截图基线留在 `tools/mobile-visual/baseline/`，
   这是零成本、长期有效的回归资产。

配套：`manifest.skin` 写成**单值**，80 行预算守得住。

## 七、最终判断

| 问题 | 回答 |
|---|---|
| 能实现"皮肤自由"吗？ | **A 档能，B 档能且比 v3 想的便宜，C 档不该做** |
| 架构可维护吗？ | **能**——契约（token / modelSlice / manifest）+ 断言（引擎换模块图）+ 视觉基线，三者齐了 |
| 扩展性强吗？ | **强**——新增皮肤 = 2 个 CSS 文件 + manifest 一行；新增视图 = 一个满足契约的组件 |
| 最大风险 | **P0a 断言引擎**（低估 1 天）与 **P2b ChatView**（4,138 行 + 45 hook 归位） |
| 建议 | 先做 **P0a + P-1 + P3-lite（3 天）**，这三件不动 UI 但决定后面是否返工 |
