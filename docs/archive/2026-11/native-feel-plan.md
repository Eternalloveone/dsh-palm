# 原生体验（native-feel）方案

> 结论：**能做到"接近原生"，差距集中在 4 处浏览器不可控项**；其余 6 项都能做，总量约 4 天。
> 关键认知：原生感 80% 来自三件事——**1 步到达、瞬时反馈、转场连贯**，不是动画花哨。

---

## 一、能拿到的 vs 拿不到的

| 能力 | 能不能 | 说明 |
|---|---|---|
| 安装到主屏、独立窗口（无地址栏） | ✅ | 已有 manifest + `ios-install-hint.tsx`，补齐 Android 引导即可 |
| 页面转场（推进 / 返回，双向） | ✅ | 现有 `PAGE_TRANSITION_MS = 260`，但只是淡入；要做成位移+双缓冲 |
| 边缘侧滑返回（自定义） | ⚠️ 部分 | Android 可用 `history.back()` + 手势；iOS 浏览器占用边缘手势，只能做"应用内二级面板"的滑动关闭 |
| 下拉关闭面板 | ✅ | 现有 sheet 已有滑入动画，补一个拖拽跟随即可 |
| 长按 / 触感（振动） | ⚠️ 部分 | `navigator.vibrate` 仅 Android；iOS 无 API |
| 惯性滚动 / 粘性头 | ✅ | 已具备（`-webkit-overflow-scrolling`、`position: sticky`） |
| 安全区 / 键盘避让 | ✅ | meta 已含 `viewport-fit=cover` + `interactive-widget=resizes-content`；已有 `useKeyboardInset` |
| 骨架屏 / 乐观发送 | ✅ | 感知速度的最大来源，成本低 |
| iOS 橡皮筋回弹 | ❌ | 浏览器级行为，无法完全自定义 |
| iOS 侧滑返回系统手势 | ❌ | 被浏览器占用 |
| 键盘弹起动画与页面同步 | ❌ | iOS 上 `visualViewport` 有固有延迟 |

**一句话：能被用户感知的"像 App"，90% 在可控范围内。**

---

## 二、原生感的三个真实来源（按性价比排序）

| 排序 | 做什么 | 为什么最有效 |
|---|---|---|
| 1 | **高频路径 1 步到达** | 3 步 → 1 步的体验提升，超过所有动画 |
| 2 | **瞬时反馈**：点击立刻变（乐观更新 + 骨架屏） | 等待感是"网页感"的第一来源 |
| 3 | **转场连贯**：推进从右滑入、返回从左滑出，且**保留滚动位置** | 断层的切换最像网页 |

动画只是第 3 名的装饰，不是主体。

---

## 三、架构落点：新增交互内核（P1.6）

放在 `ui/`（机制件），预算 ≤400 行：

```
ui/
├─ transition/         页面转场：双缓冲 + transform 动画（禁布局属性）
├─ gesture/            边缘滑动、下拉关闭、长按（已有）、拖拽跟随
├─ feedback/           触感 + 乐观更新 hook + 骨架屏基元
└─ safe-area/          安全区与键盘 inset 的统一出口
```

**五条断言**：

| # | 断言 | 防什么 |
|---|---|---|
| 1 | 转场只许动 `transform` / `opacity` | 触发重排导致掉帧 |
| 2 | 转场期间旧屏必须仍在 DOM（双缓冲） | 白屏闪烁 |
| 3 | 每个手势必须提供键盘/无障碍替代路径 | 只能滑动才能操作 |
| 4 | 触感必须可关闭，且 iOS 上静默降级 | 报错 / 骚扰 |
| 5 | 骨架屏必须在首帧渲染，晚于数据返回即判红 | 假装有骨架屏 |

## 五、验收指标（可测，不靠感觉）

| 指标 | 目标 |
|---|---|
| 首页 → 聊天 点击步数 | 1 步（配合布局重做的方向 A） |
| 转场 p95 帧耗时 | ≤16ms（现有 `tools/mobile-perf` 可测） |
| 点击到首帧反馈 | ≤100ms（乐观更新，不等网络） |
| 返回后滚动位置保持 | 100%（含长会话） |
| Long Task 数（进聊天页） | 不高于现状 |

## 六、与已有方案的接口

| 方案 | 关系 |
|---|---|
| v3.2 L1/L2/L3 | 视觉与布局的"静态"自由度 |
| **本方案 P1.6** | **交互的"动态"体验层**（转场/手势/反馈） |
| 布局重做 D0–D5 | 走"1 步到达"，是原生感的最大来源 |

三者不冲突，P1.6 依赖 `ui/` 内核，不碰业务。
