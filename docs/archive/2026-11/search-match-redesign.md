# 会话内搜索：匹配与跳转重设计

> 2026-11-13。触发：手机端「版本」搜索显示 1/2，同屏可见 4 个高亮；自动跳转要等翻页，太慢。

## 结论

把「计数」和「跳转」都建在同一套**屏幕坐标系**上（已渲染的块级文本），索引只负责回答
"未加载的历史里还有没有"。自动跳转从"翻到最早一处"改成"就近一处"，不自动跨页。

- 计数立即等于屏幕上的高亮数（不再出现 1/2 却有 4 个高亮）。
- 首次跳转 < 100ms（已加载区）/ < 400ms（最多翻一页）。
- 只改客户端即可先拿到 80% 收益（2 小时）；块级索引是第二期。

## 一、实测现状（为什么"还是不准 / 慢"）

| 观测 | 事实 | 影响 |
| --- | --- | --- |
| 手机搜索「版本」 | 显示 `1/2`，同屏 4 个高亮 | 计数来自宿主返回的命中条数，高亮来自 DOM 出现次数，**两套坐标** |
| 本机索引库 | 该会话 1838 个事件只索引了 **11 条正文**；`版本` 只落在 2 条文档（其中一条含 4 处） | 即使计数口径改成"处"，全历史也只能数到 5，不是屏幕上的真实数 |
| 会话 seq 704–980、992–1828 | 索引整段缺失（`indexed_through_seq=1838` 但中间没有文档） | 索引覆盖是机会式的，**会漏**；不能作为计数依据 |
| 自动跳转 | 目标 = 命中数组第 0 条 = 最早一处；不在当前窗口就 `loadOlder` 逐页翻 | 1838 条历史的会话可能要翻十几页，每页一次宿主读取 |
| 手机当前宿主 | 仍在旧进程上（计数 2 = 按消息段；按处应为 5） | 上一轮改动需重启宿主 + 手机硬刷新才生效 |

结论：这不是"匹配算法"单点问题，是**坐标系 + 覆盖 + 跳转方向**三处结构问题。调 debounce、
调上限都救不了。

## 二、业界做法对照

| 项目 | 计数口径 | 跳转口径 | 可借的点 |
| --- | --- | --- | --- |
| Chrome / Edge 页内查找 | 只数**已渲染** DOM 文本节点，= 高亮数 | 当前文档内就近 | 计数与高亮同源，永远不会对不上 |
| VS Code 查找 | 全量文本模型（内存），增量扫描 | 行号 + 列号 | 计数、跳转、高亮共用一套坐标 |
| Telegram / Slack | 服务端召回"消息条数"，常显示 `200+` | 按消息 id 加载邻页 | 计数分层（精确/近似）是通行做法 |
| Notion / Linear | 块级索引，命中到块 | 滚到块 | 块是最小稳定单位，不受虚拟化影响 |
| ripgrep | 流式早停，不追求全量计数 | — | 召回用字面量预筛 + 确认，快 |

共同点：**计数和高亮必须是同一次扫描的产物**；跨历史的精确计数只在"能廉价全量扫描"时成立，
否则如实显示近似值。

## 三、方案 A：屏幕优先 + 块坐标（推荐）

### 3.1 坐标系

- 渲染层给每个可搜块一个稳定 id：markdown 段落 / 表格行 / 列表项 / 代码块 / 用户气泡正文。
  `data-block-id="<messageId>:<partId>:<blockIndex>"`。
- 命中 = `(blockId, blockIndexInText)`；不再用"行内第几个 `<mark>`"或"消息段序号"。
- 渲染器与搜索器共用同一个 matcher（大小写、全半角、CJK 不分词），从根上消掉"高亮 4 个、
  计数 2 个"的偏差。

### 3.2 计数

1. 本地扫描已渲染块 → 精确得到 `localHits`（顺序、块内序号）。
2. 宿主索引只回答：未加载区还有没有、大约几处（`remoteHasMore`）。
3. 显示规则：
   - 未加载区没有 → `3/7`（精确）。
   - 有 → `3/7+`（7 = 本地精确，`+` = 后面还有，翻到边界后变精确）。
4. 禁止"数字先走、高亮没到"：`at` 只在高亮进入视口后 +1（现有行为，保留）。

### 3.3 跳转

1. 自动跳转 = **就近**：以视口 35% 为锚，先向下找最近一处，没有则向上；在已渲染区直接滚（<100ms）。
2. 未加载区不自动翻页，只提示「后面还有 N 处，按下一个继续」——与浏览器/编辑器一致。
3. 「上一个 / 下一个」到边界才翻页；翻页期间锁定当前高亮，落地后再移动，避免"数字乱跳"。
4. 方向性懒加载：向下走到末尾才请求更新的一页，向上走到开头才请求更早一页（复用现有分页）。

### 3.4 索引（第二期）

- `docs` 按**块**切分（一条 = 一个可渲染块），存 `blockId`、`blockIndex`、`offset`；
  召回直接回块坐标数组，一处一条。
- 补覆盖：增量推进 + 缺口回填（当前 1838 事件只入 11 条的洞必须先修，否则"未加载区还有几处"
  本身就不可信）。
- 召回侧沿用 FTS5 bm25 + 字面量预筛；客户端仍以本地扫描为准。

## 五、不做什么

- 不追求"匹配瞬间知道全历史精确总数"——业界没人这么做，代价是几十倍索引复杂度。
- 不再用"消息段条数"当分数，也不再用"第 N 个 mark"当坐标。
- 不在自动跳转里翻页：慢的根因是方向错了，不是翻页慢。

## 七、口径统一（2026-11-13 二修）

用户反馈「点上下跳转，数字在动，但没有跳过去」，并问是不是把思考内容也算进了匹配。
**是的，问题就在这**：宿主索引只收「用户气泡 + 助手结论」，而客户端本地计数当时扫的是
`row.text` + `flow` 里所有正文——过程步骤的叙述、思考链都被算进去了。于是计数偏大，
定位时 `marks[occurrence]` 越界退回第一个高亮，看起来就是「数字在动、画面不跳」。

| 修法 | 落地 |
| --- | --- |
| 语料口径唯一真源 | `searchCorpusOf`（原 `host/search-text.ts`）搬到 `mobile/render/search-corpus.ts`，宿主入库与客户端计数共用；判据：用户气泡正文 / 助手 answer（`processModel` 的答案，剥掉思考、工具块、围栏代码） |
| 过程/思考/工具一律不算 | 多步回合只取最后一步文本；`turn`/`command`/无答案助手行整行不算 |
| 定位坐标精确到 part | 本地命中带 `partId`（`body`/`answer`），`locateSeq` 在该 part 节点内数第 occurrence 个 `<mark>`，不再在整行里猜 |
| 剥离规则共用 | `stripToolBlocks` 搬到 `shared/strip-tool-blocks.ts`（宿主与手机端同一份） |

**回归证据**：新增单测 5 条（思考里的词不算、多步只数最后一步、过程行整行不算、代码围栏、
同文去重）与 ChatView 用例 2 条（思考 3 次 + 答案 1 次 → `1/1`；只有思考 → `无命中`）全部通过；
真机 search 组 4/4——`会话 → 6 处，296ms`、`编译 → 1/1+`（宿主已重启，`matchedTotal` 生效）；
全量 vitest 3711 通过、`guard` 16、`pnpm build` 成功。

## 八、系统性收口（2026-11-13 终版）

七轮真机反馈（1/2 却有 4 个高亮 → 点了不动 → 2/16 跳 16/16 → 跳到过程条 → 数字还偏）反复
指向同一件事：**同一条命中在四种坐标里各算一遍**（索引条数、行内第 N 处、本地文本偏移、DOM 序号）。
收口不是再修一处，而是只留**一套坐标、一条跳转路径**。

### 8.1 唯一坐标系

```
SearchMatch = { messageId, partId, offsetInPart }
```

| 来源 | 与这个坐标的关系 |
| --- | --- |
| 宿主索引 hits | `messageId` + `partId` + `matchIndex` = `offsetInPart` |
| 渲染出的 `<mark>` | 用 `closest('[data-message-id]')` / `[data-part-id]` + 同容器内序号反算 |
| 客户端本地计数 | 不再"按行文本推算"：直接遍历 DOM 的 mark，得到同一组坐标 |

计数 = 这组 matches 的长度；过程/思考/工具/代码块不产生 mark，因此**天然不进计数**。

### 8.2 一条跳转路径

`gotoRenderedMatch(match)`：切焦点行 → 滚到那一格（同一行内 14 处也逐格）。
- 已渲染 → 立即滚（本地，<100ms）；
- 未渲染（词在更早历史）→ 翻一页、落地后按坐标重放一次。**只有用户手势会触发翻页**，
  自动落点永不翻页。

删掉的三套机制：几何"下一个 mark"快通道（nudge）、"整行第 N 处"的 occurrence 推算、
按行文本的本地命中推算。翻页/轮次跳转仍用 `locateSeq`（它们要的是"第几轮"，不是"第几处"）。

### 8.3 降级矩阵（不假装）

| 条件 | 表现 |
| --- | --- |
| 索引未建 / 宿主无 `node:sqlite` / `fallback:true` | 顶部「索引建立中」，只给屏幕内计数 |
| 索引覆盖不全（`indexComplete=false`） | 分母带 `+`（至少这么多） |
| 词只在未加载历史 | `0/N+`，不自动翻页；按「上一个」才翻 |
| 宿主读历史失败 | 顶部错误条 + 「加载更早」保留可重试 |
| 未来列表虚拟化 | 计数需改成"窗口内精确 + 索引数"，这是唯一的已知改造点 |

### 8.4 契约（把七轮事故钉死）

- ChatView 搜索组 15 条：计数=高亮数、思考/过程不出高亮、同一行逐格、绕回禁止、
  空页收按钮、翻页落地、长文展开、意图对齐、`+` 降级。
- `local-search-hits` 18 条：按处计数、代码围栏、多步只取最后一步、过程行整行不算、
  就近落点、几何退化、更早命中。
- 真机 playbook（`tools/mobile-verify` search 组 5 条）：首页 21 处高亮、
  会话内计数形状、`会话 → 14 处 329ms`、点下一个后画面真的移动。

### 8.5 还没做的两件（已知边界，不是 bug）

1. 块级索引 + 覆盖回填 → 去掉分母的 `+`（约 3 天，收益仅"更精确的未加载数"）。
2. 虚拟化预案 → 一旦给列表加虚拟滚动，计数口径必须同步改（见 8.3 最后一行）。

## 九、导航模型（2026-11-13 第五修：为什么"上一个跳到 34/34"根治不了）

### 9.1 病根：两个下标被当成一个用

之前的实现里同时存在两个下标：

- `chatSearchAt` —— **屏幕 mark 的下标**（0..已渲染处数-1）
- 计数显示的 `at` —— `olderOffset + chatSearchAt + 1`（全历史第几处）

点「上一个」时，"回绕到最后一处"用的是**屏幕下标**（`n-1`），而显示又加了偏移。
屏幕 27 处、全历史 34 处（偏移 7）时，回绕得到 `7 + 26 + 1 = 34` —— 于是 8/34 按一下变 34/34。
只要"屏幕下标 + 偏移"这套拼装还在，边界永远会算错一次。

### 9.2 业界怎么做的

| 产品 | 导航状态 | 到边界 | 定位单位 |
| --- | --- | --- | --- |
| Chrome / Safari 页内查找 | 当前是第几个**结果**（不是 DOM 节点） | 回绕 | 文本节点 + 偏移 |
| VS Code 搜索结果 | 结果列表的 current index | 禁用按钮（不回绕） | 文件 + 行 + 列 |
| Slack 搜索 | 结果列表 index | 禁用 | message id |
| Notion / Obsidian | 块序列 index | 回绕 | block id + 块内偏移 |

共同点：**只有一个有序结果序列 + 一个 index，计数就是 index+1**；
"未加载"由列表的虚拟化/分页承担，导航只对 index 做加减，不参与坐标换算。

### 9.3 本项目的模型（已落地）

```
hits   = 索引逐处结果（messageId, partId, matchIndex），归一化升序     ← 序列
index  = chatSearchAt（0 起，唯一状态）                                ← 游标
count  = (index + 1) / hits.length  （+ 表示索引未覆盖全历史）           ← 显示
goto   = hits[index] → 屏幕上按 (messageId, matchIndex) 找到那格 → 容器 scrollTop
         找不到（还在未加载区）→ 翻页 → 落地后按同一身份再找一次
```

导航规则：

- 「下一个」：`index + 1`；到末位回绕到 0（末位之外没有更新内容，回绕在眼前循环）。
- 「上一个」：`index - 1`；在 0 处再按 = 还有更早历史就翻页（8/34 → 7/34 那一侧），
  真到头才回绕到末位。
- 宿主结果还没到时（第一次搜索的 200ms 内）：用屏幕上的 mark 兜底，保证点击有反应。

### 9.4 为什么这次能根治

- 计数与导航**共用一个下标**，不再有"偏移 + 屏幕下标"的转换点 → 边界不可能算错。
- 定位按**身份**（messageId + matchIndex）而不是"第几个 mark" → 未加载/合并行/同一行多处
  都不会串位。
- 屏幕仍只标「用户消息 + 结论正文」；过程/思考/工具不产生 mark，因此不进序列。

### 9.5 已知边界（不假装）

| 条件 | 表现 |
| --- | --- |
| 索引覆盖不全（`indexComplete=false`） | 分母带 `+` |
| 命中全在未加载历史 | 自动落点不翻页；用户按「上一个」才翻 |
| 未来列表虚拟化 | 序列仍成立（index 与 hits 解耦于 DOM），只需把 goto 换成 scrollToIndex |
