# 排队条 / 目标条重构方案的实现评估

> 2026-11-10。评估对象：`docs/queue-refactor-plan.md`。
> 方法：读代码 + 真机抓包实测（不是推演）。

## 0. 结论

| 问题 | 答案 |
|---|---|
| 能否实现？ | **能**，而且比方案初稿更省：原估 2 天 → **1.5 天** |
| 最难的"身份"这块要宿主配合吗？ | **不要**。实测队列行已带 `requestId`、已发送消息已带 `source.rpcId` |
| 架构上能否达成"正确"？ | **能**，但有边界：正确性可以做到"不画错"，不能做到"零延迟"（取决于宿主推帧） |
| 最大风险 | 不是技术，而是**改动面**（store 是核心，7 条病症都压在它身上） |

## 1. 两条决定性实测（推翻/加强方案的关键）

| # | 事实 | 证据 |
|---|---|---|
| F1 | 队列行**已经**带客户端生成的 `requestId` | 真机抓 `mobile.sessionState`：`queue[0] = {id:"76e47aa9…", placement:"queued", text:"（身份探针二…）", editable:true, requestId:"be1ba6de-f060-4cae-a7f1-7ca51157d0b3"}` |
| F2 | 已发送的用户消息**已经**带同一个 id（在 `source.rpcId`） | 真机抓 history 的 `user/message`：`source: {kind:"user", rpcId:"f6d60baf-…"}`（5 条里 2 条有，另 3 条是 time-context 等系统消息） |

推论：**整条生命周期可以用 id 串起来**

```
乐观项(requestId) → 宿主队列行(requestId) → 用户消息(source.rpcId) → 已发送
```

文本匹配（`spoken()`、steering 同文去重、legacy lastUserText）**从此可以降级为兜底**，
而不是主判据。这是"架构级根治"与"再打一层补丁"的分界线。

### 1.1 顺带发现的死代码

`host/queue-inbox.ts:121 rememberRequestBody()` 只被导出、**没有任何调用点**（`git grep` 全仓仅 3 处：定义、import、export）。
说明身份来自 DSH 回显，这个"投递桥"是给**不回显**场景准备的备份。方案里"需要宿主配合"的判断是错的，
但这座桥要保留并补一条守门测试（否则下一个人会当它死代码删掉）。

## 4. 架构能否保证正确性：四条可验证的不变量

| # | 不变量 | 怎么证明 |
|---|---|---|
| **I1** | 同一 `requestId` 在一屏内**至多一行** | 单元测试：乐观项 + 队列行 + 用户消息三者同 id → 可见行数恒为 1 |
| **I2** | `phase` **单调不回退**（queued→claimed→sent） | 只由 `turn/start` / `user/message(seq 递增)` 推进；乱序帧被 seq 拦掉 |
| **I3** | 视图是纯函数、**TTL = 0** → "时间"不再是正确性输入 | 删掉 3 个常量后 `grep QUEUE_.*_MS` = 0 |
| **I4** | 目标条只认投影 `revision`，命令不回显状态 | 单测：命令在途时显示"处理中"，投影到达后以投影为准 |

**覆盖度**：7 条病症里 6 条由 I1–I4 直接消除；
第 7 条「已发送仍显示排队」的**残留窗口**从"最长 90s + 猜错"缩到"宿主下一次推帧"——
这是宿主节奏，客户端无法再优化。

## 5. 不能靠架构消除的三条硬约束（必须写进文档，别承诺过头）

| 约束 | 表现 | 应对 |
|---|---|---|
| 投影延迟 | 你发出去了，队列条最多再存在一帧时间 | 身份 + 版本保证"不会一直挂着"，不保证"瞬间消失" |
| 桌面端入队的行没有 `requestId` | 这类行只能文本兜底 | 兜底范围限定为"非本机发出的行"，误判影响小 |
| DSH 某版本不再回显 `rpcId` | 身份链断 | `rememberRequestBody` 桥 + 一条守门测试，接线 2 行 |

---

## 6. 建议的最小可行版本（MVP）

**只做 S1 + S2 + S3（身份接线 + 删 TTL + phase），不动 UI，约 6.5h**：

- 能消掉 7 条里的 5 条：双份显示、删除后复活、长回合消失、旧快照回撤、已发送残留；
- 视觉零变化 → 可以单独上线、单独回滚；
- 行为等价由现有 77 项队列测试 + 新增 ~15 项守住；
- UI 合并（S4/S5）作为第二次独立上线，风险隔离。

## 7. 缺口已被测试证明（2026-11-10 实测）

写了两条临时测试（跑完即删），结论是**明确的**：

| 测试 | 结果 | 含义 |
|---|---|---|
| 队列行(requestId=X) + 乐观项(requestId=X) | **通过** | 乐观项退场已经是**按身份**的（`session-status.ts:397-399`），不是文本 |
| 队列行(requestId=X) + user/message(rpcId=X)、`spokenTexts` 为空 | **失败**（返回 1 行，期望 0） | **消费侧没接身份**：`visibleQueue` 根本没有"已发送的 rpcId 集合"这个输入，只能用正文猜 |

所以方案里 S3 的工作量是"加一个输入 + 一条判据"（1h），而不是"重新设计身份"。
这也解释了为什么会出现「已经发出去了还显示排队」——不是身份丢了，是身份没被用上。
