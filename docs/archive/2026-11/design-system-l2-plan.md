# 移动端设计系统方案（简洁 / 高内聚 / 可扩展）

> 基线事实（先纠正一个常见误解）：`mobile-styles.ts` 9,378 行是**构建产物**，真源是
> `src/mobile/styles/` 下 42 个按序号拼接的 CSS 文件；token 已经存在（`design/tokens.ts`，
> 225 行）。所以**不是从零建，是把已有的东西收成三层**。

---

## 一、现状：地基有，缺中间的"组件层"

| 层 | 现在有没有 | 状态 |
|---|---|---|
| **L0 token** | ✅ 有 | `design/tokens.ts`：明暗两套调色板 + 字阶/圆角/间距，有测试 |
| **L1 基础样式** | 🟡 半有 | 42 个 CSS 文件按序号拼接（`010-base` → `420-goal-bar`），顺序靠文件名 |
| **L2 组件** | ❌ 缺 | 没有可复用的组件层；9 个页面各写各的 JSX + 直接挂 876 个类名 |
| **L3 页面** | ✅ 有 | 9 个视图，10,309 行，其中 ChatView 占 40% |

**缺口就是 L2。** 所以"重写 UI"的正确做法不是重写页面，而是**补上 L2，再让页面逐步换用**。

---

## 二、方案：三层 + 两组不变量

```
L0  token（已有，补语义层）
      ├── 原语：--indigo-500、--space-3、--radius-lg
      └── 语义：--surface、--text-1、--border、--accent、--danger   ← 新增，页面只用语义层
L1  基础类（保留现有 42 个 CSS 文件，加前缀与 @layer）
L2  组件（新增，每个组件 = 一个 .tsx + 一个 .css + 一个 props 类型）
L3  页面（9 个视图，逐步换成 L2 组件）
```

### 2.1 两条不变量（这是"高内聚低耦合"的全部内容）

1. **数据只从上面来**：L2 组件**不许** import `api.ts` / store / hook；只接收 props + 回调。
2. **样式只向下走**：页面能用 `p-*` 类与语义 token；组件不许写页面级布局（`margin` 影响外部）。

违反这两条，组件层就会变成"第二个 ChatView"。

### 2.2 命名与分层（一次定死，永不改）

| 约定 | 规则 | 为什么 |
|---|---|---|
| 类名前缀 | 所有新类 `p-`（palm）；旧类**不批量改名**，随迁移逐个替换 | 876 个类一次改完必炸；逐个换可回滚 |
| 样式分层 | `@layer reset, token, base, component, page, overlay` | 现在靠文件名序号，加新文件就得挑号；`@layer` 后顺序由声明决定 |
| 组件 CSS 文件 | 一个组件一个文件，**≤200 行**，与 tsx 同名同目录 | 找样式不用翻 42 个文件 |
| 变体 | 用 `data-*` 属性，不用类名爆炸 | `p-button[data-variant="ghost"]` vs `.p-button--ghost` |
| 尺寸 | 只有 `sm / md / lg` 三档 | 现在是自由数字，同一个按钮有 5 种高度 |

## 三、组件清单（12 个，按"用得最多"排序）

| # | 组件 | 替代现在什么 | 主要 props |
|---|---|---|---|
| 1 | `PButton` | `.icon-btn` / `.btn` / 各种 `<button>` | `variant` / `size` / `icon` / `loading` |
| 2 | `PSheet` | `sheets.tsx` 里的底部浮层 | `open` / `onClose` / `title` / `children` |
| 3 | `PListRow` | 会话列表、设置项、命令列表 | `leading` / `title` / `meta` / `onPress` |
| 4 | `PCard` | 回合卡片、市场卡片 | `header` / `children` / `status` |
| 5 | `PInput` | 输入框、设置项输入 | `value` / `onChange` / `multiline` / `invalid` |
| 6 | `PChip` | 命令 chip、附件 chip、标签 | `tone` / `onRemove` |
| 7 | `PDialog` | 重命名、删除确认 | `open` / `title` / `actions` |
| 8 | `PState` | 空态 / 错误 / 加载（三合一） | `kind` / `title` / `action` |
| 9 | `PSkeleton` | 现在已有 `130-skeleton.css` | `lines` / `height` |
| 10 | `PToast` | 现在已有 `320-toast.css` | 已有，收编进组件层 |
| 11 | `PDisclosure` | `190-disclosures.css`（20KB 的折叠） | `title` / `open` / `children` |
| 12 | `PMedia` | 图片预览 / 灯箱 / 代码块 | `kind` / `src` / `lang` |

**12 个够不够？** 现在 876 个类里，真正被 3 个以上页面用到的形态只有这些。其余是页面专属布局，**不该进设计系统**——设计系统一旦什么都收，就会变成第二个大文件。

---

## 四、治理：三条断言（防止重新变烂）

| 断言 | 拦什么 |
|---|---|
| L2 组件目录里**不许出现** `import ... from '../api.ts'` 或 store | 组件偷偷直连数据 |
| 组件 CSS 文件 **≤200 行** | 单片样式膨胀 |
| 新类名必须以 `p-` 开头（除旧类白名单） | 命名失控 |

这三条都能写成测试，进现有 `architecture.test.ts`（已有 14 条，同款写法）。

## 五、迁移顺序与工时

| 阶段 | 内容 | 工时 | 产出 |
|---|---|---|---|
| D0 | 语义 token（在原 225 行上加 20 个变量）+ `@layer` 声明 | **0.5 天** | 页面可用语义变量 |
| D1 | 12 个组件（先做 1/2/3/8 四个最常用的） | **1.5 天** | 能覆盖 60% 现有 UI |
| D2 | 三条治理断言 | **0.5 天** | 防回退 |
| D3 | 迁一个页面验证（建议 SettingsView，783 行，风险最低） | **1 天** | 证明方案可行 |
| D4 | 其余页面逐屏迁移 | 每屏 1~2 天 | — |

**先做 D0–D3（3.5 天）**，能拿到"方案已验证"的结论，再决定要不要铺开。

---

## 六、为什么这套方案"简洁"

| 常见做法 | 本方案的选择 | 理由 |
|---|---|---|
| 引入 Tailwind / CSS-in-JS | **不引入**，继续构建期拼 CSS | 现在是零运行时成本；引框架等于把 876 个类翻译一遍 |
| 一次重命名所有类 | 只给**新**类加前缀 | 876 个类批量改必炸，且无法逐个回滚 |
| 组件尽量薄、逻辑放 hook | 组件**只接收 props + 回调** | 手机端的坑（键盘、长按、滚动）都在交互里，组件里越复杂越难测 |
| 一套组件同时服务桌面与移动 | 移动端独立实现，**共享 token 契约** | 桌面是鼠标/键盘，移动是触摸，共用组件会写出两套分支 |

---

## 七、一句话结论

**补一层 12 个组件的 L2，用三条断言守住边界，先花 3.5 天做出并验证，再铺开。**

不做的话：9 个页面会继续往那 42 个 CSS 文件里加类，ChatView 重写完也还是同样的结构。
